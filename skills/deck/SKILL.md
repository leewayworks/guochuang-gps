# Deck

Apply the shared policies in `gps-common`. When saving a Markdown report, use the common project-name rule with topic `PPT`.

Design the deck as a sequence of reviewer decisions. Each slide needs one conclusion, one visual job and one evidence pointer.

## Build the sequence

A common technical or venture spine is:

value in one sentence -> real problem -> field finding -> intervention -> mechanism -> baseline and metric -> validation -> user or scene -> alternatives -> IP and student work -> customer and economics -> growth -> social value -> ask.

Change the order when the track demands it. For an industry project, make the chain visible: enterprise question -> response -> demonstrator -> expert questions. For red-tour, show participation and beneficiary change early.

## Slide contract

For each page fill: no, purpose, headline, visual, evidence_ids, speaker cue, risk and cut priority.

The headline should state the conclusion, not the topic. Put units, sample size, date and source beside a number. Keep project-book, slide and spoken figures identical. Label image-only pages visual review required; missing extracted text is not proof that a page is empty.

## Time cuts

Prepare three versions:

- Full: the complete argument and supporting proof.
- Review: remove decorative pages and keep one proof page per major claim.
- Rescue: keep value, problem, mechanism, strongest result, user evidence, team ownership and the next step.

Never cut the only baseline, limitation or student-contribution evidence. Timing, page count, font and effects are local rules until the 2026 evaluation notice or a school or provincial notice confirms them.

## Final QA

Check headline clarity, legibility, source and date, units, number consistency, ownership, privacy, transitions, screen readability and unsupported superlatives. End with the two claims the team wants the reviewer to remember and the evidence that supports each.
