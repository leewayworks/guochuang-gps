# Anonymous case patterns for project positioning

Load this reference when an Agent needs to turn project materials into a defensible positioning, select the strongest claim, or diagnose why a polished claim still feels weak.

These patterns are distilled from historical materials at source level `L4`. They are calibration aids, not current rules, official scoring criteria, or award predictors. Apply a pattern only when the project's own evidence supports it. Never copy historical wording, numbers, screenshots, identities, or confidential facts.

The source base uses one shared count: **67 national gold-award project sets** across three tracks, practical input from **17 national-gold contestants** and **5 expert judges**, and **9 anonymous method cards**. Counting rules are recorded in [method-sources.md](method-sources.md).

## Operating vocabulary

### Evidence roles

Use roles to describe what a source proves. A file can serve more than one role, but repeated items from the same origin do not become independent evidence.

| Role | What it must establish |
|---|---|
| `problem` | The need exists in a defined user, site, workflow, or enterprise context. |
| `baseline` | The relevant incumbent, threshold, prior state, or alternative is explicit. |
| `mechanism` | A technical or organizational action plausibly produces the claimed result. |
| `result` | A measured outcome is tied to a condition, period, unit, and source. |
| `independent_validation` | A party or record outside the claim-making loop confirms performance, delivery, finance, or social effect. |
| `field_use` | The solution entered a real workflow rather than only a controlled demonstration. |
| `transaction` | Intent, purchase, payment, acceptance, or repeat business is distinguished by stage. |
| `persistence` | The result continued, repeated, improved, or transferred to another setting. |
| `ownership` | Student decisions, work products, version history, and rights are attributable. |
| `limitation` | Conditions, uncertainty, negative results, and remaining risks are disclosed. |

### Maturity stages and claim ceiling

| Stage | Strongest defensible claim |
|---|---|
| `concept` | A reasoned hypothesis or proposed mechanism. |
| `prototype` | A function has been demonstrated in an identifiable prototype. |
| `controlled_test` | Performance has been measured against a baseline under stated conditions. |
| `field_pilot` | Value has been observed in a real scenario with a traceable user or partner. |
| `acceptance_or_transaction` | A customer, enterprise, or institution has accepted delivery or exchanged value. |
| `replication` | Results have persisted or transferred across periods, sites, customers, or partners. |

Do not let a narrative pattern raise a claim above the evidence-supported maturity stage.

### Track names used below

- `main`: main track, where innovation, product, customer, business, and team must form a coherent venture.
- `red`: Youth Red Dream Building Journey, where beneficiaries, field continuity, co-creation, and sustainable social mechanisms dominate.
- `industry`: industry proposition track, where proposition clauses, enterprise interfaces, delivery, and acceptance dominate.

## Pattern cards

### CP-COG-001 — Six-stage risk removal

- **Applicable context:** Use as the top-level positioning skeleton when materials contain many disconnected strengths or the Agent must choose what comes first. It works across tracks and stages.
- **Judge question:** Is this a real need, does the response make sense, is the result credible, can it enter practice, did the students do the work, and can the value persist or scale?
- **Narrative sequence:** Establish the real need -> explain why the old approach fails -> show the distinctive response -> validate the result -> prove field adoption or delivery -> attribute student contribution -> show persistence or replication. If a risk remains open, state it rather than skipping over it.
- **Required evidence roles:** `problem`, `mechanism`, `result`, `ownership`; add `independent_validation`, `field_use`, and `persistence` before making strong delivery or scale claims.
- **Maturity gate:** May diagnose any stage. A complete six-stage story normally requires at least `field_pilot`; claims of durable advantage or scale require `replication`.
- **Anti-patterns:** Counting highlights instead of closing risks; leading with policy, awards, or team prestige; hiding an unproven step between laboratory result and user value; treating a timeline as growth without showing new capability.
- **Track overlay:** `main` ends in customer value, transactions, and venture capability; `red` ends in beneficiary change, local partnership, and service continuity; `industry` ends in clause coverage, interface fit, enterprise testing, and acceptance.

### CP-TECH-001 — Pain–response–metric–validation mapping

- **Applicable context:** Use when a project has several pain points or innovation claims and needs a legible one-to-one structure. It is especially useful for technical decks, proposal summaries, and defense answers.
- **Judge question:** Which exact bottleneck does each innovation solve, by how much, under what conditions, and who verified it?
- **Narrative sequence:** Define pain A in a concrete workflow -> state why the baseline fails -> present response A -> select the user-relevant metric -> compare under the same conditions -> attach test or field validation -> disclose trade-offs. Repeat separately for pain B rather than merging unrelated claims.
- **Required evidence roles:** `problem`, `baseline`, `mechanism`, `result`, `limitation`; use `independent_validation` or `field_use` for any “leading,” “solved,” or “ready” claim.
- **Maturity gate:** At `concept` or `prototype`, call the response proposed or demonstrated. Call it measured only at `controlled_test`; call the pain solved in practice only at `field_pilot` or later.
- **Anti-patterns:** One innovation allegedly solves every pain; one pain is followed by a list of unrelated features; a metric has no baseline or condition; a statistically better parameter is presented without user value; “first” or “leading” lacks a search boundary.
- **Track overlay:** `main` adds willingness to adopt and economic consequence; `red` replaces purely technical metrics with accessibility or beneficiary outcomes where appropriate; `industry` maps every pain and response to a named proposition clause and enterprise threshold.

### CP-TECH-002 — Mechanism–prototype–test–field loop

- **Applicable context:** Use for hard technology, intelligent systems, equipment, or any project that risks jumping directly from theory to commercialization.
- **Judge question:** Does the claimed mechanism survive implementation, controlled testing, and real operating conditions?
- **Narrative sequence:** Explain the causal mechanism -> identify the student-built prototype and critical interface -> define the baseline and test protocol -> report measured performance and uncertainty -> expose the prototype to the real environment -> record failure, iteration, and field result -> state the remaining engineering limit.
- **Required evidence roles:** `mechanism`, `ownership`, `baseline`, `result`, `field_use`, `limitation`; prefer `independent_validation` for safety-critical, regulated, or high-stakes performance.
- **Maturity gate:** Mechanism claims may begin at `concept`; functionality requires `prototype`; superiority requires `controlled_test`; usability or readiness requires `field_pilot`; deliverability requires `acceptance_or_transaction`.
- **Anti-patterns:** Using papers or patents as substitutes for a working artifact; displaying a prototype photograph without version or test record; testing only the easiest condition; omitting failures and reliability; treating simulation as field use.
- **Track overlay:** `main` translates field performance into customer value and producibility; `red` tests usability, inclusion, local maintenance, and beneficiary access rather than novelty alone; `industry` tests compatibility, reliability, safety, and the enterprise's specified interfaces.

### CP-BIZ-001 — Customer-stage ladder

- **Applicable context:** Use whenever materials show customer names, cooperation documents, pilots, orders, or revenue. Normalize every relationship before positioning traction.
- **Judge question:** What exactly has each customer done, and how much commercial risk has been removed?
- **Narrative sequence:** Name the target segment and buying problem -> classify each relationship as `contact`, `intent`, `pilot`, `acceptance`, `paid`, or `repeat` -> link the stage to a dated source and deliverable -> identify the conversion requirement -> show movement to the next stage -> aggregate only comparable stages.
- **Required evidence roles:** `problem`, `field_use`, `transaction`, `persistence`, `limitation`; `independent_validation` is needed when acceptance or payment is asserted through a summary rather than a primary record.
- **Maturity gate:** A contact or intent does not exceed `concept`; a user trial supports `field_pilot`; acceptance, contract performance, or payment supports `acceptance_or_transaction`; repeat use or repeat payment supports `replication`.
- **Anti-patterns:** Logo walls; counting contacts as customers; treating an intention agreement as revenue; mixing cumulative and annual figures; hiding cancellations, unpaid receivables, one-off subsidies, or related-party transactions.
- **Track overlay:** `main` emphasizes conversion, payment, repeat purchase, and channel fit; `red` uses partner stages such as introduced, co-designed, adopted, institutionalized, and replicated without forcing all beneficiaries into a buyer model; `industry` distinguishes proposition contact, joint test, enterprise evaluation, formal acceptance, and follow-on deployment.

### CP-BIZ-002 — Customer value–price–unit economics

- **Applicable context:** Use when a project claims a large market, low price, high margin, or rapid growth, and the Agent must test whether the business logic connects.
- **Judge question:** What measurable value does the buyer receive, why will the buyer pay this price, and does each delivered unit create sustainable cash rather than accounting growth?
- **Narrative sequence:** Identify the buyer and budget owner -> quantify the current loss or alternative cost -> show the solution's incremental value -> explain the pricing basis -> calculate variable delivery cost and contribution margin -> include acquisition, service, capacity, and cash-cycle constraints -> run downside and break-even cases -> connect projections to verified customer stages.
- **Required evidence roles:** `problem`, `baseline`, `result`, `transaction`, `limitation`; add `persistence` for retention assumptions and `independent_validation` for audited or externally confirmed finance.
- **Maturity gate:** At `concept`, present assumptions and sensitivity only. A pricing claim needs at least a credible pilot or quotation basis. Unit economics become evidenced at `acceptance_or_transaction`; repeatability claims require `replication`.
- **Anti-patterns:** Top-down market size as demand proof; price chosen only as a discount to a competitor; gross margin omits installation, service, yield, acquisition, or working capital; forecasts are shown as current traction; precision exceeds the evidence.
- **Track overlay:** `main` uses the full buyer-value-price-margin-cash chain; `red` separates beneficiary value, payer, subsidy or cross-subsidy, and service sustainability; `industry` ties economic value to the enterprise's total cost, cycle time, risk, retrofit cost, or platform reuse.

### CP-SOC-001 — Beneficiary action–change–assurance–replication loop

- **Applicable context:** Use for `red` projects and any main-track venture making strong social-impact claims.
- **Judge question:** Who changed, what project action plausibly contributed, is the change independently traceable, and can the mechanism continue without a one-time campaign?
- **Narrative sequence:** Define the beneficiary group and prior state -> show continuous field entry and co-design -> specify the service or organizational action -> record participation and delivery quality -> compare beneficiary outcomes over time -> disclose attribution limits -> add audit, institutional, or third-party assurance -> show the local operating mechanism -> demonstrate transfer with quality control.
- **Required evidence roles:** `problem`, `mechanism`, `result`, `independent_validation`, `persistence`, `limitation`, `ownership`; use `field_use` to prove the service occurred, not merely that an event was publicized.
- **Maturity gate:** A visit or event remains `prototype` at most. Outcome claims require repeated delivery and measured change at `field_pilot`. Sustainable or replicable impact requires institutional continuity or multi-site evidence at `replication`.
- **Anti-patterns:** A moving story replaces causal evidence; participant or coverage counts are treated as outcomes; commercial income is treated as beneficiary value; a one-time event is called a mechanism; replication means only placing the same logo in more locations.
- **Track overlay:** `main` uses this loop as an impact layer but still proves customer and business viability separately; `red` makes it the central positioning spine and foregrounds co-creation, dignity, local ownership, and continuity; `industry` uses it only when the proposition explicitly includes worker, community, safety, or environmental outcomes.

### CP-IND-001 — Proposition clause–solution–delivery–acceptance loop

- **Applicable context:** Use for industry proposition entries or any co-development project judged against an enterprise brief.
- **Judge question:** Did the team understand the enterprise's actual constraints and deliver every material requirement in a form the enterprise can test and accept?
- **Narrative sequence:** Parse the proposition into atomic clauses -> investigate the enterprise's current system and constraints -> map one technical response to each clause -> agree interfaces, thresholds, and test conditions -> build and integrate the deliverable -> run joint or enterprise tests -> record clause-by-clause results and gaps -> obtain acceptance or define the next acceptance milestone.
- **Required evidence roles:** `problem`, `baseline`, `mechanism`, `result`, `field_use`, `independent_validation`, `ownership`, `limitation`; use `transaction` when acceptance, investment, procurement, or follow-on deployment is claimed.
- **Maturity gate:** Relevant prior research is only background. A credible answer begins with enterprise-specific investigation. Completion claims require integrated testing at `field_pilot`; “fulfilled” or “delivered” requires enterprise acceptance at `acceptance_or_transaction`.
- **Anti-patterns:** Retrofitting a generic laboratory result to the proposition; emphasizing enterprise prestige instead of clause coverage; showing isolated component metrics without system integration; citing meeting photographs as validation; leaving unmet clauses implicit.
- **Track overlay:** `industry` uses this as the primary spine; `main` can adapt it to customer requirements but must add market choice and venture economics; `red` can adapt “clauses” into jointly agreed beneficiary or local-partner service requirements, not corporate acceptance language.

### CP-TEAM-001 — Student contribution and capability accumulation

- **Applicable context:** Use when成果 originate from a laboratory, advisor, enterprise, family business, or long-running institution, or when the team's chronology is rich but ownership is unclear.
- **Judge question:** Which critical discoveries, designs, implementations, decisions, and iterations were performed by the students, and what durable capability did they gain?
- **Narrative sequence:** Identify the pre-existing platform and rights -> divide the project into critical work packages -> attribute each decision and artifact -> link students to dated records and versions -> show how field feedback changed their work -> connect each milestone to a new capability -> reconcile contribution with IP, equity, corporate roles, and defense answers.
- **Required evidence roles:** `ownership`, `mechanism`, `result`, `field_use`, `limitation`; primary records such as notebooks, repositories, designs, protocols, correspondence, or version histories are stronger than role titles.
- **Maturity gate:** Required at every stage. The claim ceiling for student leadership is set by attributable work, not by product maturity. Strong “student-led” positioning needs ownership across problem finding, key decisions, implementation, and iteration.
- **Anti-patterns:** Advisor or platform credentials substitute for student work; titles substitute for artifacts; students appear only in competitions or publicity; an inherited product is narrated as student-created; contribution, IP ownership, equity, and legal roles contradict one another.
- **Track overlay:** `main` emphasizes transition from research to product, customer, and venture decisions; `red` emphasizes long-term field responsibility, co-design, and organization building; `industry` emphasizes translating research into interfaces, engineering trade-offs, joint testing, and delivery.

### AP-001 — Pseudo-advantage warning and claim downgrade

- **Applicable context:** Run before finalizing a positioning statement, especially when the strongest material consists of superlatives, policy alignment, honors, expert endorsements, customer logos, large market forecasts, patents, media, or emotional stories.
- **Judge question:** If borrowed authority and presentation polish are removed, what advantage is owned by the team, compared on a fair basis, and proven by independent evidence?
- **Narrative sequence:** Extract every advantage claim -> label its source as `owned`, `borrowed`, or `unresolved` -> identify the comparison set and boundary -> attach the evidence role actually served -> detect source dependence and maturity inflation -> apply the appropriate claim ceiling -> rewrite the claim with object, context, distinctive action, result, condition, source, and limitation -> move unsupported claims to the missing-proof queue.
- **Required evidence roles:** At minimum, every retained advantage needs `baseline`, `result`, and `ownership`; add `mechanism` to explain causality, `independent_validation` for superiority or outcome claims, and `limitation` for honest scope.
- **Maturity gate:** This is a diagnostic at every stage. Policy, honors, patents, publications, endorsements, intentions, and forecasts do not advance maturity by themselves. A claim cannot exceed the stage supported by direct performance, field, transaction, or persistence evidence.
- **Anti-patterns:** “First” without search boundary; patent or paper count as product proof; macro market size as customer proof; policy relevance as effectiveness; endorsements or media as validation; intent as adoption; logos as customers; a higher parameter without equal-condition comparison; participant counts as social outcomes; forecasts as achieved finance; prestigious collaborators as student contribution.
- **Track overlay:** `main` downgrades unsupported technology, market, customer, and finance claims; `red` downgrades sentiment, coverage, publicity, and one-off activity claims without beneficiary change and continuity; `industry` downgrades enterprise prestige, meetings, or generic relevance without clause mapping, integration tests, and acceptance.

## Agent application protocol

1. Select one primary pattern that matches the judge's next unresolved question; add no more than two supporting patterns.
2. Build a claim-to-evidence map using the evidence roles above. Record source path, page or slide, date, condition, owner, limitation, privacy flag, and independence group.
3. Determine the current maturity stage from inspected evidence. Apply its claim ceiling before rewriting the positioning.
4. Apply the relevant track overlay. Do not mix track language when the underlying acceptance logic differs.
5. Run `AP-001`. Downgrade unsupported superlatives, maturity inflation, and borrowed advantages.
6. Return: the positioning sentence, selected pattern IDs, evidence-role coverage, maturity ceiling, remaining risk, and the next three proof-building actions.

Recommended positioning syntax:

`For [defined actor] in [high-value context], the team addresses [verified bottleneck] through [owned distinctive action], producing [bounded result] under [condition], supported by [evidence roles], with [remaining limitation].`

Do not mention the historical source set in user-facing project copy. Do not infer that a pattern, page order, or visual style caused an award.
